# eStables: план архитектуры и разработки PHP-движка

Статус: v7, согласован с заказчиком 26.10.2026. Базовый коммит для разработки движка: `0a21c112` (демо со всеми согласованными доработками и рабочей сортировкой перетаскиванием). Демо в `demo/` — визуальный и поведенческий эталон для движка.

## 0. Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Сервер | VPS на Debian 13 (trixie), nginx + php-fpm, есть SSH и cron, полный контроль над окружением |
| Версии | то, что в trixie stable: PHP 8.4, MariaDB 11.8 LTS. MySQL от Oracle не поддерживаем |
| Администраторы | один или несколько равноправных, без ролей |
| «Запомнить меня» | делаем: без галочки cookie живёт до закрытия браузера, с галочкой — срок из конфига (по умолчанию 1 месяц), продлевается при каждом заходе |
| Предмет в разделах | в нескольких разделах сразу, механика как у тегов; один раздел главный (первый добавленный, можно переназначить), от него строятся хлебные крошки |
| Характеристики | свободные пары «название — значение»; позже автоподбор по существующим в БД значениям |
| Адреса | `/catalog/…/` для разделов, `/item/<номер>/` для предметов |
| Каталожный номер | уникален на весь сайт; если не указан — генерируется автоматически (алгоритм позже, возможно от главного раздела) |
| Объём | единицы–десятки тысяч предметов, на предмет от единиц до десятков иллюстраций; исходники от 320×240 до современных многомегапиксельных |
| Статика | Bootstrap, иконки, GLightbox и шрифты лежат локально, без CDN |
| Картинки | при загрузке метаданные удаляются принудительно; очищенный файл сохраняется как `<SHA-256>.<ext>`, дубликаты исключаются по хешу |
| Форматы | наружу только JPEG, PNG и GIF: эти три формата сохраняются как загружены (только очистка метаданных, анимация GIF сохраняется); всё остальное конвертируется в JPEG (прозрачность — на белый фон), и этот JPEG становится оригиналом. WebP и прочее не выдаём; HEIC не поддерживаем |
| Кодирование | JPEG: качество как у исходного JPEG, но не ниже 95; из других форматов — 95. PNG: всегда сжатие 9 |
| Папки изображений | подпапки по первым двум символам хеша: `ab/abcdef….jpg` |
| Порядок предметов | ручная расстановка перетаскиванием, отдельно в каждом разделе; новый предмет встаёт в начало |
| Страница раздела | показывает только предметы, привязанные к разделу напрямую |
| Счётчики | в рубрикаторе и в шапке раздела — число различных предметов во всём поддереве (рекурсивно), как в демо |
| Сортировка у посетителя | по умолчанию всегда «Авторский» (ручной порядок); также по номеру, году, названию; выбор посетителя запоминается в его браузере и действует на всём сайте; админ и гость здесь не различаются. Настройки сортировки у раздела нет |
| GIF | оригинал как есть (с анимацией); превью в списках — первый кадр, крупный показ — с анимацией |
| Лимиты | загрузка до 50 МБ и 100 Мп; оригинал показывается вместо копии, если не больше 2560×2560; копии 400 и 1600 px |
| Оригиналы | «Скачать оригинал» доступно всем; если исходник не больше X×Y (настраивается), на странице показывается сам оригинал вместо уменьшенной копии |
| Импорт | не сейчас; когда данные будут готовы — отдельный CLI-импортёр |

## 1. Цели и ограничения

- CMS-справочник коллекционера: иерархический рубрикатор, карточки предметов с фото, характеристиками и вариантами исполнения. Публичная часть только для чтения, админка для редакторов. Свободной регистрации нет.
- Вёрстка, стили и скрипты берутся из `demo/` на коммите `0a21c112`. Разметка шаблонов должна давать тот же результат, что демо; это проверяется сравнением скриншотов движка и демо в каждой сборке. Отличия от демо допускаются только осознанные и перечисляются в описании сборки.
- **Окружение**:
  - PHP 8.4 из trixie (`php8.4-fpm`, расширения `pdo_mysql`, `mbstring`, `imagick`, `intl`, `fileinfo`; `gd` как запасной вариант);
  - для обработки изображений: ImageMagick (через `php8.4-imagick`) и `jpegtran` из `libjpeg-turbo-progs` для очистки и поворота JPEG без потерь;
  - MariaDB 11.8 LTS;
  - nginx 1.26 + php-fpm из trixie;
  - CI дополнительно гоняет PHP 8.5 как проверку на будущее, но целевая версия 8.4.
- **Зависимости**: Composer используется штатно (автозагрузчик, инструменты разработки). Сторонние библиотеки в рантайме — только при явной пользе; на старте их нет.
- **БД**: только PDO, `utf8mb4` / `utf8mb4_uca1400_ai_ci`, строгий SQL-режим.
- Самодеплой и самообновление БД с первого коммита движка.
- Авторизация на серверных сессиях: в cookie только случайный идентификатор, ни логинов, ни паролей, ни их хешей.
- Лицензия AGPLv3: ссылка на исходный код остаётся в футере.
- Чувствительные данные только в `config/config.php`; он создаётся из `config/config.template.php` вручную и уже в `.gitignore`.

## 3. Ядро

- **Front controller** `public/index.php`: автозагрузчик, конфиг, обработчик ошибок, проверка схемы БД (раздел 4), маршрутизация, ответ.
- **Роутер**: таблица маршрутов (метод + шаблон пути → контроллер), именованные маршруты и генерация URL, чтобы шаблоны не собирали адреса руками.
- **Request/Response**: тонкие объекты над суперглобалами; заголовки, редиректы, коды ответа, JSON для AJAX-действий админки.
- **Шаблоны**: чистый PHP. Общие шапка, футер и `<head>` в `templates/partials/` (копипаста из демо исчезает). Весь вывод по умолчанию проходит через хелпер экранирования; сырой HTML только явно.
- **Ошибки и журнал**: свой обработчик, журнал в `var/log/` с ротацией, страницы 404/500 в стиле сайта, подробности только при `debug = true`.
- **Конфиг** (PHP-массив):
  - подключение к БД;
  - базовый URL, флаг debug, секрет приложения;
  - сроки сессий и «запомнить меня»;
  - провайдер и ключи капчи;
  - лимиты загрузки, размеры превью;
  - часовой пояс.
- **CLI** `bin/estables` использует то же ядро: миграции, создание администратора, смена пароля, сборка мусора по фото и сессиям, проверка окружения, резервная копия.

## 4. Самодеплой и самообновление схемы БД

### 4.1. Схема по образцу Android

- Класс `Db\Schema`:
  - константа `VERSION` — целевая версия схемы для данного кода;
  - метод обновления со `switch` по текущей версии без `break`.
- Каждый `case N` переводит схему из N в N+1. Вход происходит на `case` текущей версии, выполнение идёт до конца блока. Свежая установка — вход с `case 0`, поэтому новая и обновлённая базы проходят одну и ту же цепочку.
- `case 0` создаёт таблицу метаданных схемы и базовые таблицы.
- Правила:
  - выпущенный шаг никогда не редактируется, новые только добавляются в конец;
  - каждый `case` помечен комментарием о преднамеренном проваливании (fall through);
  - шаги могут содержать и DDL, и перенос данных на PHP.

### 4.2. Отличие от Android

В SQLite весь `onUpgrade` идёт в одной транзакции и при сбое откатывается целиком. В MariaDB каждый DDL-оператор (`CREATE`, `ALTER`, `DROP`) неявно фиксирует транзакцию. Начиная с 10.6 отдельный DDL атомарен при падении сервера, но откатить его из приложения нельзя. Поэтому:

- версия схемы записывается в БД **после каждого шага**; при сбое следующий запуск продолжит с упавшего шага;
- шаг маленький (в идеале один DDL) и безопасен для повторного запуска. В MariaDB это просто: `ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `DROP … IF EXISTS`;
- переносы данных внутри шага идут в транзакции;
- перед запуском цепочки делается резервная копия: `mariadb-dump` в `var/backups/`. Если дамп не удался, обновление не начинается. Число хранимых копий задаётся в конфиге.

### 4.3. Когда и как запускается

- **Основной путь — при деплое**: `bin/estables migrate` после `git pull` / `composer install`.
- **Страховка — на запросе**. Если файлы обновили, а команду не запустили:
  - каждый запрос сверяет версию из кеш-файла `var/cache/schema.version` с `Schema::VERSION`, в БД за этим не ходит;
  - при расхождении берётся именованная блокировка `GET_LOCK('estables_schema', …)`, версия перечитывается из БД, запускается цепочка, обновляется кеш;
  - остальные запросы на это время получают 503 «Идёт обновление» с `Retry-After`.
- Если версия в БД **больше**, чем в коде (откатили файлы, но не базу), движок отказывается работать и показывает понятную ошибку. Автоматических даунгрейдов нет.

### 4.4. Первый запуск

1. Нет `config/config.php` → страница с инструкцией: скопировать шаблон и заполнить. Пароли через веб-форму не принимаем и в файлы не пишем.
2. Конфиг есть, база пустая → `bin/estables check` (или та же проверка на запросе) проверяет окружение: версию PHP, расширения (`imagick` или `gd`), наличие `jpegtran`, права на запись в `var/` и `public/media/`. Затем цепочка с `case 0`.
3. Пользователей нет → основной путь `bin/estables create-admin`. Веб-форма первого администратора тоже есть, но доступна только по одноразовому токену из `var/install.token` и отключается после создания первого пользователя.

### 4.5. Тесты миграций

- Свежая установка до последней версии даёт ту же схему, что поэтапное обновление с каждой ранее выпущенной версии (сравнение `SHOW CREATE TABLE`).
- Повторный запуск каждого шага ничего не ломает.
- Имитация сбоя посреди цепочки с последующим продолжением.

## 5. Авторизация и сессии

### 5.1. Cookie

- В cookie только случайный идентификатор (`random_bytes`, 256 бит). Никаких логинов, паролей и хешей.
- Флаги: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, собственное имя. Сайт работает только по HTTPS, HTTP перенаправляется.
- Сессионных cookie у гостей нет: сессия появляется только при входе. На публичных страницах у гостя может появиться только выбранная им сортировка (раздел 8), и только после того, как он сам её выбрал. Ещё одна короткоживущая cookie защищает формы входа и установки (см. CSRF в 5.4). Публичные страницы остаются без сессии, это хорошо и для кеширования, и для приватности.

### 5.2. Хранение сессий

- Сессии хранятся в БД, в собственном хранилище без стандартного `$_SESSION`.
- В таблице лежит **SHA-256 от идентификатора**, а не он сам: утечка базы не даёт готовых cookie.
- Поля: пользователь, режим «запомнить», время создания, последней активности и истечения, IP и User-Agent для списка входов, данные сессии.
- Это даёт выход из всех сессий, список активных входов и принудительное завершение при блокировке пользователя.

### 5.3. «Запомнить меня»

Работает на той же сессии; отдельного токена и хешей учётных данных нет.

- **Без галочки**: cookie без `Expires`/`Max-Age`, живёт до закрытия браузера. На сервере дополнительно действует таймаут бездействия (по умолчанию 12 часов, настраивается). Это нужно потому, что браузеры с функцией «восстановить вкладки» хранят такие cookie сколь угодно долго.
- **С галочкой**: cookie с `Max-Age` из конфига (по умолчанию 30 дней), серверный срок такой же.
  - Срок скользящий: при заходе продлевается и в БД, и в cookie. Чтобы не писать в базу на каждом запросе, продление выполняется не чаще раза в N минут (настраивается).
  - Идентификатор периодически меняется (например, раз в сутки). Старый ещё минуту принимается для параллельных запросов. Это сужает окно, в котором украденная cookie остаётся рабочей.
- **Для обоих режимов**:
  - смена идентификатора при входе;
  - строгий режим (неизвестный идентификатор не принимается и новую сессию не создаёт);
  - выход удаляет запись на сервере и cookie.

### 5.4. Остальное

- **Пароли**: `password_hash()` с Argon2id (в PHP 8.4 из trixie он есть) и `password_needs_rehash()` при входе. Ошибка входа не говорит, что неверно — логин или пароль.
- **Защита от перебора**: таблица попыток, ограничения по логину и по IP в скользящем окне с временной блокировкой (задержку ответа не делаем: она занимает воркеры php-fpm и сама становится способом DoS). Капча на форме входа показывается всегда. На уровне сервера можно добавить fail2ban по журналу неудачных входов (пример фильтра в `deploy/`).
- **CSRF**:
  - на страницах админки токен хранится в серверной сессии;
  - на форме входа и в мастере установки сессии ещё нет: токен подписывается секретом приложения, содержит время (HMAC) и привязан к случайному значению в короткоживущей cookie формы (double submit). Без такой привязки токен можно было бы получить заранее и подставить в чужую форму. Cookie ставится только на этих страницах и удаляется после входа;
  - проверка обязательна для всех POST, включая AJAX. Любые изменения данных только через POST.
- **Капча как модуль**: интерфейс «показать виджет / проверить ответ», реализации — заглушка для разработки, Cloudflare Turnstile, Google reCAPTCHA; провайдер выбирается в конфиге. Anubis — не виджет, а proof-of-work прокси перед сайтом; на VPS он ставится перед веб-сервером, а движок в этом случае использует заглушку.
- **Гость и администратор**: видимость ссылок в футере и кнопки «Редактировать» определяет сервер при рендеринге. Демо-эмуляция через `localStorage` в движок не переносится.

## 6. Модель данных (первая версия схемы)

| Таблица | Назначение и ключевые поля |
|---|---|
| `schema_meta` | версия схемы, служебные значения |
| `users` | логин (уникальный), хеш пароля, отображаемое имя, активен, даты создания и последнего входа |
| `sessions` | SHA-256 идентификатора (PK), пользователь, флаг «запомнить», создание, активность, истечение, предыдущий хеш и время его действия (для ротации), IP, UA, данные |
| `login_attempts` | логин, IP, время, успех |
| `rubrics` | родитель, slug (уникален в пределах родителя), название, заголовок, описание, порядок, видимость, обложка (ссылка на изображение), `path` (материализованный путь `/1/4/12/`) |
| `items` | каталожный номер (уникальный; генерируется, если не указан), slug адреса (уникальный, из номера), название, краткое и полное описание, статус (черновик / опубликован), годы выпуска от/до, даты, автор изменений |
| `item_rubrics` | связь многие-ко-многим: предмет, раздел, признак главного раздела, дата добавления связи, позиция предмета в этом разделе |
| `images` | SHA-256 очищенного файла (PK), расширение (`jpg`/`png`), ширина, высота, размер, исходный формат до конвертации, дата загрузки |
| `item_photos` | предмет, изображение (SHA-256), подпись, порядок; первое по порядку — обложка |
| `attribute_names` | словарь названий характеристик (для подсказок и будущих фильтров) |
| `item_attributes` | предмет, название из словаря, значение, порядок |
| `item_variants` | предмет, номер варианта, исполнение, годы, порядок |
| `slug_history` | старые адреса разделов и предметов для 301-редиректов |
| `settings` | название сайта и прочие настройки из админки |
| `audit_log` | кто, когда и что изменил |

### Разделы как теги

- `item_rubrics` связывает предмет с любым числом разделов. Главным становится первый добавленный раздел, в редакторе его можно переназначить. От главного раздела строятся хлебные крошки, «соседние модели» и «из той же серии»; остальные разделы перечисляются на странице предмета.
- Ровно один главный раздел на предмет гарантирует сам движок (в транзакции при каждом изменении связей). В MariaDB нет частичных уникальных индексов, поэтому БД это ограничение напрямую не проверяет.
- Страница раздела показывает только предметы, привязанные к нему напрямую; предметы подразделов видны на страницах подразделов.
- Счётчик раздела в рубрикаторе и цифры в шапке раздела («моделей», «вариантов», «годы выпуска») считаются по всему поддереву: число **различных** опубликованных предметов, так что предмет из двух подразделов одного родителя у родителя учитывается один раз. Сама страница при этом показывает только прямые привязки.
- **Ручной порядок** хранится в `item_rubrics.position`, то есть отдельно для каждого раздела: один и тот же предмет может стоять первым в одном разделе и десятым в другом.
  - Позиции хранятся с шагом (например, 1024). Перемещение пишет одно новое значение посередине между соседями; когда промежуток исчерпан, раздел перенумеровывается целиком в одной транзакции.
  - Индекс (раздел, позиция) даёт быструю выдачу страницы раздела в ручном порядке.
  - Новый предмет в разделе встаёт в начало: позиция = минимальная в разделе минус шаг (позиции знаковые, отрицательные значения допустимы).
- Удаление раздела:
  - предметы, у которых этот раздел единственный, нужно перенести или удалить (как в демо);
  - у остальных связь просто снимается; если снят главный раздел, главным становится следующий по дате добавления.

### Дерево рубрик

Список смежности плюс материализованный путь. Рубрик сотни (при десятках тысяч предметов), поэтому дерево читается одним запросом и кешируется в `var/cache/`; кеш сбрасывается при любом изменении рубрикатора. Цифры раздела («моделей», «вариантов», «годы выпуска») — агрегаты, кешируются вместе с деревом.

### Поиск

- `FULLTEXT` (InnoDB) по названию, описаниям, номеру и значениям характеристик.
- Точное совпадение номера ищется отдельным запросом.
- При десятках тысяч предметов `FULLTEXT` справляется без внешнего поискового движка.
- Минимальную длину слова (`innodb_ft_min_token_size`) и стоп-слова проверить на реальных русских данных.

### Характеристики

- Свободные пары с общим словарём названий.
- Задел на автоподбор:
  - подсказки названий берутся из словаря;
  - подсказки значений — из `DISTINCT` по уже введённым значениям этого названия;
  - индекс на (название, значение) закладывается сразу.

## 7. Изображения

### 7.1. Приём и очистка

- Тип определяется по содержимому (`finfo` + Imagick), а не по имени файла. Лимиты: размер файла и число мегапикселей (настраиваются; размер согласуется с `client_max_body_size` / `upload_max_filesize`).
- **JPEG, PNG и GIF сохраняют свой формат**, метаданные удаляются без перекодирования пикселей:
  - JPEG: `jpegtran -copy icc` убирает EXIF, XMP, IPTC и комментарии, но сохраняет цветовой профиль ICC (он нужен для правильных цветов и личных данных не содержит). Если в EXIF указан поворот, он применяется без потерь (`-rotate`, `-transpose` и т. п.): иначе после удаления тега снимок с телефона лёг бы на бок;
  - PNG: из файла вырезаются текстовые и служебные блоки (`tEXt`, `zTXt`, `iTXt`, `eXIf`, `tIME`), пиксельные данные не трогаются;
  - GIF: из файла вырезаются блоки комментариев и application-расширения с метаданными (XMP и подобные); расширение `NETSCAPE2.0`, отвечающее за повтор анимации, сохраняется. Кадры, палитра и задержки не меняются, анимация остаётся;
  - запасной путь для JPEG без `jpegtran`: разбор маркеров файла средствами PHP.
- **Любой другой формат** (WebP, AVIF, BMP, TIFF и т. д.) конвертируется в JPEG через Imagick:
  - прозрачность закрашивается белым;
  - у анимированных файлов (например, WebP) берётся первый кадр;
  - получившийся JPEG становится оригиналом, исходный файл не сохраняется.
- **Параметры кодирования** (везде, где Imagick записывает файл — при конвертации и для уменьшенных копий):
  - JPEG из JPEG: качество исходника, которое Imagick оценивает по таблицам квантования, но не ниже 95;
  - JPEG из любого другого формата: 95;
  - PNG: уровень сжатия 9 всегда (сжатие без потерь, влияет только на размер файла и время записи);
  - GIF, превью для списков: первый кадр, уменьшенный и записанный как статичный GIF;
  - GIF, крупный показ: кадры уменьшаются по отдельности (`coalesce` → масштабирование → оптимизация кадров), палитра пересчитывается, задержки и повтор сохраняются; если оригинал не больше 2560×2560, показывается сам оригинал;
  - очищенный через `jpegtran` оригинал не перекодируется вовсе, к нему эти правила не относятся.
- **Имя файла**: SHA-256 **очищенного** файла, расширение `jpg`, `png` или `gif`. Поэтому одинаковые снимки, различающиеся только метаданными, тоже распознаются как дубликаты.
- **Дубликаты**: если файл с таким хешем уже есть, новый не пишется, а предмет ссылается на существующую запись `images`. Если это изображение уже прикреплено к тому же предмету, загрузка отклоняется с понятным сообщением.

### 7.2. Хранение и выдача

- **Очищенные оригиналы** лежат в `public/media/originals/ab/<sha256>.<ext>`, где `ab` — первые два символа хеша (256 подпапок, в каждой при сотнях тысяч файлов окажется по несколько сотен или тысяч). Оригиналы доступны всем по прямой ссылке.
- **«Скачать оригинал»** идёт через движок (`/download/<sha256>/<имя>`): он проверяет, что изображение существует, и отвечает заголовком `X-Accel-Redirect`, а сам файл отдаёт nginx. Имя файла читаемое, вида `lfz-1042-1.jpg`, с `Content-Disposition: attachment`.
- **Уменьшенные копии** того же формата, что оригинал (JPEG → JPEG, PNG → PNG, GIF → GIF):
  - путь `public/media/<размер>/ab/<sha256>.<ext>`;
  - фиксированный набор размеров из конфига, например превью 400 px и показ 1600 px по длинной стороне;
  - увеличение не делается никогда: исходник 320×240 так и показывается в 320×240.
- **Оригинал вместо копии**: если исходник не больше X×Y (по умолчанию, например, 2560×2560; настраивается), на странице и в полноэкранном просмотре показывается сам оригинал, а копия крупного размера не создаётся.
- **Генерация копий по запросу**:
  - nginx отдаёт файл, если он есть (`try_files`); если нет, запрос уходит в движок;
  - движок проверяет, что размер есть в разрешённом списке, а хеш — в таблице `images`, создаёт копию под блокировкой и отдаёт её;
  - так нет очереди задач, а пересборка после смены размеров сводится к удалению папки размера;
  - `bin/estables media:warm` заранее создаёт копии для всего каталога (например, после смены размеров).
- **Память**: многомегапиксельные исходники обрабатываются Imagick с ограничением ресурсов (`memory`, `map`, `area` из конфига), а не GD, которому на 50 Мп нужны сотни мегабайт.

### 7.3. Удаление

- Отвязка фото от предмета файл не удаляет.
- `bin/estables gc` по cron удаляет изображения, на которые больше никто не ссылается (ни предметы, ни обложки разделов), спустя заданную задержку, вместе со всеми их копиями.
- Тот же `gc` чистит истёкшие сессии и старые попытки входа.

### 7.4. Безопасность и объём

- В `public/media/` nginx не передаёт ничего в php-fpm, кроме фиксированного маршрута генерации копий; имена файлов генерирует только движок.
- Раскладка по 256 подпапкам держит размер каждой папки разумным даже при сотнях тысяч файлов.

## 8. Публичная часть

- **Адреса**:
  - раздел: `/catalog/figurki/farfor/lfz/`;
  - предмет: `/item/lfz-1042/`;
  - slug раздела получается транслитерацией русского названия, slug предмета — из каталожного номера; оба можно править вручную;
  - при смене slug — 301-редирект через `slug_history`.
- **Страницы**:
  - раздел: подразделы, предметы раздела (только прямые привязки), фильтр по десятилетиям, сортировка, плитка/список, пагинация;
  - предмет: галерея с кнопкой «Скачать оригинал», характеристики, варианты, описание, соседние модели, «из той же серии» (по главному разделу), список остальных разделов, где лежит предмет;
  - «О справочнике»: текст владельца сайта в HTML; пока он в шаблоне, позже — правка из админки;
  - поиск, 404.
- **Сортировка**:
  - варианты: «Авторский» (ручной порядок раздела), по номеру, по году, по названию; по умолчанию всегда «Авторский», отдельной настройки у раздела нет;
  - выбор посетителя сохраняется в cookie `es_sort` (срок — год, без персональных данных) и становится его сортировкой по умолчанию на всём сайте; админ и гость не различаются;
  - именно cookie, а не `localStorage`: порядок нужен серверу при отрисовке страницы и пагинации, иначе пришлось бы пересортировывать на клиенте или делать лишний переход;
  - параметр `?sort=` в адресе действует на конкретную ссылку и сильнее cookie, чтобы ссылку с нужной сортировкой можно было переслать; каноническим адресом страницы считается вариант без параметра;
  - выбор темы, как и сейчас, остаётся в `localStorage`: он влияет только на стили, серверу его знать не нужно.
- **SEO**:
  - `<title>` и описание, канонические адреса, Open Graph с обложкой;
  - `sitemap.xml` и `robots.txt`;
  - админка и вход закрыты `noindex`.
- **Производительность**:
  - статика в `public/assets/` с версией в адресе и долгим кешированием;
  - ленивые изображения, `srcset` из превью;
  - публичные страницы без сессии можно кешировать на уровне nginx (микрокеш), если понадобится; ключ кеша учитывает cookie сортировки.

## 9. Админка

- **Рубрикатор**:
  - создание, правка, видимость;
  - перестановка перетаскиванием — собственная реализация на Pointer Events из демо (мышь, палец, клавиатура);
  - удаление по правилам раздела 6.
- **Порядок предметов в разделе**:
  - отдельный режим списка предметов «в разделе N»: перетаскивание внутри страницы, кнопки «выше/ниже»;
  - при десятках тысяч предметов перетаскиванием между страницами не обойтись, поэтому есть действия «в начало», «в конец», «на позицию…» (в том числе как массовое действие для выделенных).
- **Предметы**:
  - список с поиском, фильтрами и пагинацией;
  - массовые действия: «Переместить» превращается в «Добавить в раздел» / «Убрать из раздела», плюс публикация, снятие с публикации, удаление;
  - редактор: выбор нескольких разделов с отметкой главного, фото, характеристики с подсказками, варианты, статус; пустой каталожный номер генерируется при сохранении.
- **Фото**: загрузка (в том числе нескольких файлов сразу), подписи, порядок, обложка; повторно загруженный файл распознаётся по хешу.
- **Пользователи**: список, добавление, блокировка, смена пароля, список активных сессий с завершением.
- **Все изменения** только через POST + CSRF. AJAX отвечает JSON; без JS формы работают обычной отправкой там, где это реально.

## 10. Безопасность (сквозное)

- Только подготовленные выражения PDO, никакой сборки SQL из пользовательских данных.
- Экранирование вывода по умолчанию в шаблонах.
- Заголовки: строгий `Content-Security-Policy` (благодаря локальной статике без внешних доменов, кроме капчи), `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors`, HSTS.
- Загружаемые файлы никогда не исполняются; в публичные исходники попадают только очищенные от метаданных файлы JPEG, PNG и GIF.
- Секрет приложения подписывает служебные токены: токен установки, CSRF формы входа.

## 11. Качество и CI

- GitHub Actions:
  - `php -l`, PHPStan (уровень 8+), PHP-CS-Fixer (PER Coding Style, преемник PSR-12);
  - PHPUnit с сервисом MariaDB 11.8, PHP 8.4 (плюс 8.5 как необязательная проверка на будущее).
- Визуальные тесты: Playwright-скрипт сравнения скриншотов из рефакторинга превращается в проверку «страница движка = страница демо» для каждой готовой страницы.
- Существующий workflow публикации демо на Pages не трогаем.

## 12. Развёртывание и обновление

- **Первичная установка** (`docs/INSTALL.md`):
  - пакеты из trixie;
  - пользователь и база MariaDB;
  - `git clone`, `composer install --no-dev`;
  - заполнение `config.php`;
  - `bin/estables migrate`, `bin/estables create-admin`;
  - пакеты: `nginx`, `php8.4-fpm`, `php8.4-mysql`, `php8.4-mbstring`, `php8.4-intl`, `php8.4-imagick`, `libjpeg-turbo-progs`, `mariadb-server`, `composer`;
  - конфиги nginx и php-fpm из `deploy/`, HTTPS через Let's Encrypt (certbot);
  - cron или systemd timer для `bin/estables gc` и ежесуточной резервной копии.
- **Обновление** (`docs/UPGRADE.md`): `git pull`, `composer install --no-dev`, `bin/estables migrate`. Если последнюю команду забыть, схема обновится сама на первом запросе.
- **Резервные копии**: ежесуточный `mariadb-dump` и копия `public/media/originals/`. Папки уменьшенных копий бэкапить не нужно: они пересоздаются.
- **Диск**: исходники бывают крупными; объём под `public/media/originals/` стоит заложить с запасом и следить за ним.

## 13. Этапы и сборки

### 13.1. Правила

- Каждый коммит по движку — **сборка**, которую можно развернуть в LNMP-песочнице (nginx + php8.4-fpm + MariaDB 11.8) по `docs/INSTALL.md` и проверить в браузере. Непроверяемых «голых» коммитов движка нет.
- К каждой сборке прилагаются:
  - список того, что готово и должно работать, с шагами проверки в браузере;
  - перечень отличий от демо (что из демо ещё не перенесено и почему);
  - для схемы БД — какие шаги миграции добавлены.
- Перед выдачей сборка разворачивается в песочнице, проходится в браузере и сверяется со скриншотами демо.
- Коммиты подготовки среды (инструменты разработки, вендорная статика, документация) этому правилу не подчиняются.
- Каждая сборка обновляет схему БД только добавлением новых шагов в `Schema`; уже выпущенные шаги не меняются.
